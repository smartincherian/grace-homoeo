# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Homoeo Desk" (originally "Grace Homoeo") — an installable multi-clinic PWA for homoeopathy clinics, built with **Vite + React + TypeScript + MUI + Firebase**. Hosted on Firebase Hosting; data lives in Cloud Firestore on the **`grace-homoeo`** Firebase project.

**Status:** Auth, the adaptive app shell, multi-clinic tenancy (superadmin, owners, seats), and the Patients & Consultations, Inventory, Funds, Calculator and Bookings (slot booking) modules are built. Each clinic can set its own name, logo, colour, scripture banner and contact details (owner Settings page). See `docs/superpowers/specs/` and `docs/superpowers/plans/`. Anyone with a verified email can self-sign-up at `/setup` and gets a 21-day free trial (see Self-signup and trial). The old Bible-in-a-Year helper is intentionally out of scope.

**Live:** the multi-clinic cutover and all four Homoeo Desk phases (roles, branding, staff, booking) were deployed together (rules + hosting) on 2026-10-21 to https://grace-homoeo.web.app. Grace's data lives in `clinics/grace-homoeo` (owner `brigittarinny1989@gmail.com`, seat 1). The empty test clinics `grace` and `test` remain, and the legacy top-level collections (incl. one old-format `consultation` doc) are still there until a later cleanup. Migration (`--resync`) must not be re-run now that the rules are live.

## Architecture

- **Entry & providers** — `src/main.tsx` renders the provider stack in order: `QueryClientProvider` → `ThemeProvider` + `CssBaseline` → `ToastProvider` → `BrowserRouter` → `App`. Toast sits above the router so route components can call `useToast`.
- **Routing** — `src/App.tsx` (react-router v6): `/login` is public; `/verify-email` is the verified-email gate; `/setup` (outside `<AuthGuard>`, `src/features/signup/`) is self-signup for verified users with no allow-list entry (`getAccess` returns `"signup"`; unassigned entries still get "not allowed"); `/admin` is the superadmin page (clinics, owners, seats); clinic pages live under `/:clinicSlug/patients|inventory|calculator|funds|bookings…` (`bookings?day=YYYY-MM-DD`, open to every member) plus owner-only `/:clinicSlug/people` (add/remove the clinic's users) and `/:clinicSlug/settings` (branding and contact details) and the owner-only staff module `/:clinicSlug/staff`, `staff/new`, `staff/:id`, `staff/:id/edit`, `staff/:id/leaves/new`, `staff/:id/leaves/:leaveId/edit`, `staff/payroll` (behind `<OwnerOnly>`; rules are the real gate), behind `<AuthGuard>` inside `<AppShell>`. Legacy `/patients/…` paths redirect to the member's own clinic; `/` and unknown paths go to `/<own clinic>/patients` (superadmin: `/admin`). The URL is navigation only; Firestore rules enforce clinic isolation. Hosting rewrites all paths to `/index.html` (`firebase.json`).
- **Feature-folder structure** — code is organized by feature under `src/features/` (all built: `auth/`, `access/`, `patients/`, `consultations/`, `inventory/`, `funds/`, `people/`, `settings/`, `staff/`, `bookings/`, `rateCalculator/`). Shared building blocks live in `src/components/`, `src/lib/`, and `src/theme/`. Features must not import each other's internals — only shared modules.
- **Firebase layer** — `src/lib/firebase.ts` initializes Firebase from `import.meta.env.VITE_FIREBASE_*` and exports `auth` and `db`. It connects to local emulators when `VITE_USE_EMULATOR=true`. Feature data access goes through typed per-collection repositories + TanStack Query hooks + zod schemas (the established pattern); UI never calls the Firestore SDK directly.
- **Auth** — Firebase Auth via Google or email/password; a verified email is required (unverified password users are sent to `/verify-email`). Access comes from the allow list + seats; roles are superadmin/owner/member. `useAuth()` exposes `{ user, loading }`; `AuthGuard` shows a spinner while resolving, then renders children or redirects to `/login`. `ensureUserDoc` creates `users/{uid}` (`uid, email, displayName, role`) on first login, with `role: "superadmin"` for the superadmin email, else `"admin"`; `users.role` is self-written and never grants permission.
- **UI stack** — MUI v6 styled via the `sx` prop; theme in `src/theme/theme.ts`, built per clinic from the brand colour (default `#2f6bff`, see Theming). `AppShell` is adaptive: a bottom navigation bar on mobile, a permanent left sidebar on desktop — same features on both. Global feedback goes through `ToastProvider` / `useToast` (in `src/components/useToast.ts`) — never `alert()`. `QueryStates` (`src/components/QueryStates.tsx`) renders loading/empty/error/`children` for every list view.
- **Theming** — the accent `TOKENS` (`blue`, `blue50`…) are CSS variables (`--brand`, `--brand-hover`, `--brand-50…700`, `--brand-rgb`) set per clinic by `BrandScope` from the clinic's `primaryColor`, passed through `ensureContrast` (4.5:1 on white). Use `TOKENS`/`GRADIENT`, never a raw accent hex. Only the Settings preview uses literal hex.
- **PWA** — `vite-plugin-pwa` (config in `vite.config.ts`) emits the manifest + service worker; icons in `public/`. The app is installable to a phone home screen.

## Data model (Firestore)

**Roles:** superadmin (`smartin.cherian@gmail.com`, manages clinics/owners, belongs to no clinic), owner (one per clinic, `clinics/{id}.ownerEmail`, manages `/people`), member. Max 3 users per clinic, enforced by `clinics/{id}/seats/{1|2|3}` = `{ email }`; each `allowedEmails/{email}` carries `clinicId` + `seat` (owner = seat 1).

**Multi-clinic:** all clinic data lives under `clinics/{clinicId}/…` (`patients, consultations, generals, lsmc, inventory, orderItems, expenses, counters/patients`); `clinics/{clinicId}` holds `{ name, createdAt, ownerEmail, timeZone }` (`timeZone` is `Asia/Kolkata`) plus a `seats` subcollection and the slug is the doc ID. `allowedEmails/{email}` carries `clinicId` + `seat` (one clinic per email); `users/{uid}` stays top-level. Collection descriptions below are per clinic. See `docs/superpowers/specs/2026-10-19-multi-clinic-design.md`. Cutover order: `npm run migrate:clinics` (dry run, then real) -> verify (every source doc ID must exist at the destination; re-run only with `--resync`, only BEFORE deploying, never after) -> `npm run backfill:seats` (dry run, then real; after any final resync) -> `firebase deploy --only firestore:rules,hosting` immediately -> close and reopen the app on every device (the first open may still run the old cached PWA, which reads legacy collections the new rules deny) -> tell existing password users they must verify their email once -> do not create a second clinic until the rules deploy is confirmed (hosting with the old catch-all rules would let any allow-listed member read every clinic) -> delete legacy top-level collections later. (Done for `grace-homoeo` on 2026-10-21, except the legacy cleanup.)

Target collections (see the design spec for full field lists):

- `settings/branding` (per clinic, `clinics/{id}/settings/branding`) — `displayName` (≤60), `logoDataUrl` (`""` or `data:image/(png|webp|jpeg);base64,…`, ≤200000 chars; logo resized client-side to ≤256px, no Storage), `primaryColor` (`#rrggbb`), `showScripture`, `contact{doctorName, qualifications, registrationNo, address, phone, email}` (each ≤120), `updatedAt`, `updatedBy`. Owner/superadmin write; rules validate the shape and limits; all members read. Accessed via `useBranding`/`useSaveBranding` (`src/lib/`), cached in localStorage. `"settings"` is a reserved slug.
- `users` — `{ uid, email, displayName, role }` (`ensureUserDoc` writes `role: "superadmin"` for the superadmin email, else `"admin"`; self-written and never grants permission).
- `patients` — `serialNo`, `name`, `nameLower`, `dob`, `gender`, `place`, `phone`, `createdAt`, `lastVisitAt`.
- `consultations` — **top-level** (not nested), with `patientId` + denormalized `patientName`/`serialNo` so Funds can total income across all visits while a patient's history stays a simple query.
- `inventory` — `name`, `nameLower`, `quantity`, `unit`, `reorderLevel`, `notes`, `updatedAt`.
- `expenses` — `date`, `category`, `amount`, `note` (income comes from consultation `amount`; balance = income − expenses).
- `staff` (**owner/superadmin only**) — `name`, `nameLower`, `phone`, `designation`, `joinedOn`, `leftOn?`, `monthlySalary`, `active` (`leftOn === null`), `createdAt`. Never deleted; set `leftOn`.
- `leaves` (owner-only) — `staffId`, `staffName`, `from`, `to` (clinic-zone day starts, inclusive), `halfDay`, `type` (Casual/Sick/Unpaid; only Unpaid is deducted), `note`, `createdAt`. A leave touching an already-paid month sets that payment's `needsReview`.
- `salaryPayments/{staffId}_{YYYY-MM}` (owner-only) — `staffId`, `staffName`, `month`, `base`, `paidDays`, `unpaidDays`, `deduction`, `adjustment`, `adjustmentNote`, `net`, `paidOn`, `paymentMode`, `needsReview`. Salaries stay out of `expenses`; the owner's Funds page adds a "Salaries" line (sum of `net` by `paidOn`) into expenses and balance (members' Funds never queries it). Funds periods use the device zone while `paidOn` is a clinic-zone day start (harmless for India).
- `settings/schedule` (`clinics/{id}/settings/schedule`; owner/superadmin write, members read) — `slotMinutes` (5–120; UI offers 10/15/20/30/45/60), `weekly{mon…sun: [{start,end}]}` (≤3 sessions per day), `holidays[{date, note}]` (≤100, clinic-zone day starts), `updatedAt`, `updatedBy`. `src/lib/schedule.ts` (`slotsForDay`, `holidayOn`, `offGridAppointments`, `useSchedule`/`useSaveSchedule`); edited in Settings via `ClinicHoursSection`. `saveSchedule` drops past holidays and throws `OffGridError` (listing the appointments) if any appointment that hasn't ended (`end > now`, any status) would no longer fall on a slot, so slot length/hours cannot change under existing bookings.
- `appointments/{startEpochMs}` (members) — `date` (clinic-zone day start), `start`, `end`, `patientId?`, `patientName` (≤80), `phone` (≤20), `serialNo?`, `status` (`booked|arrived|done`), `note` (≤200), `createdBy`, `createdAt`, `consultationId?`. The doc ID is the slot start so a slot holds one appointment: `bookAppointment` (`features/bookings/bookingsRepo.ts`) is a transaction that throws `SlotTakenError` if the doc exists; rules also require create status `booked`, `createdBy` = caller and a future `end`, and updates cannot change `start/end/date/createdAt/createdBy`. Holidays have no slots (not bookable); bookings that already exist on a holiday stay and are flagged in the day view. The day view and Today strip poll every 60s so a second device's changes show up. Cancel / no-show is a batch (`closeAppointment`): create the `appointmentHistory` copy and delete the appointment together (rules: delete needs the history doc via `existsAfter`; history create needs the appointment gone).
- `appointmentHistory/{start}_{createdAt}` (members read; create-only, never updated/deleted) — the 12 appointment fields plus `closedAt`, `closedBy`; `status` is `cancelled|no-show`.
- **Booking links** — `src/lib/appointmentLink.ts` (`linkableAppointment`, `clampedLink`): registering a patient or saving a consultation from an appointment updates it best-effort (`patientId`/`serialNo`, `consultationId`, `status`), and a cancelled/done/missing/unreadable appointment never blocks the patient or consultation save (the link is read before the serial is taken, and a failed linked commit is retried once without the link). `TodayAppointments` (`src/components/`) shows today's appointments on the Patients page.
- **Admin controls** (`/admin`, superadmin only; `features/access/clinicAdminRepo.ts`) — clinics are listed in a table (rows expand to their users). `clinics/{id}.active` and `allowedEmails/{email}.active` (missing = active) turn a whole clinic or one user off: rules deny every clinic read/write (the clinic doc itself stays readable), the seat is kept, and `AuthGuard` shows an "inactive, contact the administrator" screen via `getMembership().inactive`. Only the superadmin can change `active`. Delete clinic (type the slug to confirm) removes the clinic's `allowedEmails`, then every `CLINIC_COLLECTIONS` subcollection page by page, then the clinic doc; it is not undoable and can be re-run after a failure. Keep `CLINIC_COLLECTIONS` in sync with the rules.
- `counters/patients` — `lastSerial`; patient serial numbers are assigned atomically via `nextPatientSerial()` in `src/lib/serial.ts` (a Firestore transaction), not by scanning all patients.
- **Clinic-zone dates** — day starts and `YYYY-MM` months for staff/payroll use `clinics/{id}.timeZone` via `src/lib/zonedDates.ts`, never the device zone. `"staff"` and `"bookings"` are reserved slugs (like `"settings"`).
- **Phase 3 release** — the staff module ships as its own release (`firebase deploy --only firestore:rules,hosting`); the new rules must go live with the hosting.
- **Self-signup and trial** — `src/lib/subscription.ts` holds `TRIAL_DAYS` (21), `TRIAL_MS`, `WHATSAPP_NUMBER` (919036209639), `clinicStatus`, `trialOk` and `pricingWhatsAppUrl`. `clinics/{id}` gains `trialEndsAt` (every new clinic: createdAt + `TRIAL_MS`), `authorized`, `authorizedAt`, `selfSignup`; legacy clinics without `trialEndsAt` count as OK. `SetupPage` + `signupRepo` (`createOwnClinic`, `isSlugTaken`) create clinic + owner `allowedEmails` + seat 1 in one batch (`createdAt` within ±10 min of `request.time`). Rules `trialOk(c)` (authorized, or no `trialEndsAt`, or `now < trialEndsAt`) and `canWrite(c)` gate every non-superadmin write under `clinics/{id}/…` and owner `allowedEmails` writes: an expired trial is read-only, reads unchanged, superadmin exempt (so `deleteClinic` still works). `get` of a non-existent clinic is allowed (slug check). `reservedSlugs()` in the rules mirrors `RESERVED_SLUGS` (now incl. `setup`, `signup`). `TrialBanner` (`src/components/`) shows days left; `src/lib/writeDenied.ts` + the `MutationCache` `onError` in `src/lib/queryClient.ts` open a "Trial ended" dialog (WhatsApp pricing link) on permission-denied writes in an expired clinic. `/admin` shows status chips (Authorized / Trial · N days left / Trial ended / Legacy / Self signup), Authorize / Remove authorization in the row menu (`setClinicAuthorized`) and an "Authorized (no trial)" checkbox on create.

Before deploying, verify production has no orphan `clinics/{slug}` subcollections without a parent clinic doc (a self-signup could claim that slug). After deploying, authorize `grace-homoeo` on `/admin`.

## Conventions & gotchas

- **Firebase config is env-only.** Real values live in `.env.local` (git-ignored); never hardcode keys in source. `.env.example` documents the variable names.
- **Tests must pass in a clean checkout.** A committed `.env.test` holds dummy Firebase values so Vitest (which runs in `test` mode) initializes the SDK without the developer's `.env.local`. Without it, `getAuth()` throws `auth/invalid-api-key`. Don't delete `.env.test`.
- **Testing** — Vitest + React Testing Library, TDD. Unit tests **mock** `firebase/firestore` (e.g. `serial.test.ts`, `ensureUserDoc.test.ts`), so `npm test` needs no emulator; the emulator config exists for manual/integration use.
- **Storage formats** — dates as **epoch milliseconds** (number); money as **rupee numbers** (displayed with `₹`).
- **Firestore rules** (`firestore.rules`) require a signed-in user with a **verified email** (everyone, incl. superadmin) and allow only listed clinic subcollections (patients, consultations, generals, lsmc, inventory, orderItems, expenses, counters; plus appointments and appointmentHistory (members), and `settings/schedule` (members read, owner/superadmin write, like branding), owner/superadmin-only staff, leaves, salaryPayments; anything else is denied). Existing password users must verify their email once after the rules deploy. Previously they only required sign-in; they are structured to be role-aware for future tightening. Be careful before deploying rules.
- **Rules tests / emulator.** `npm run test:rules` needs the Firestore emulator, and the firebase CLI (15.x) needs JDK 21+. On Java 17 use `npx -y firebase-tools@13.35.1 emulators:start --only firestore --project demo-grace` (or `emulators:exec`) instead.
- **Hosting** — `firebase.json` deploys the same `./dist` (SPA rewrite to `/index.html`) to two sites on the `grace-homoeo` project: `grace-homoeo.web.app` and `homoeodesk.web.app` (both in Auth's authorized domains). `firebase deploy --only hosting` updates both.
